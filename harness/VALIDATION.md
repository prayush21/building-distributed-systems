# Validation against libCacheSim

Generated by `harness/validate.py`. Do not edit by hand.

Cross-check of this harness's replayer against libCacheSim on real
traces, at identical cache sizes with identical object-size handling.

## Result

**PASS** — 72 of 72 FIFO/LRU/LFU points agree within the required 0.001 absolute request miss ratio.

- Worst FIFO/LRU/LFU disagreement: `1.11e-16`
- Worst disagreement across all 6 policies, including S3-FIFO, SIEVE and Belady: `1.11e-16`
- 144 comparison points total

Every difference is at the floor of float64 summation order. The two
implementations are not merely close; they are making identical
eviction decisions on every request.

## Reproducing

```
pip install libcachesim
harness/fetch_traces.sh harness/traces
go build -o /tmp/replay ./cmd/replay
python3 harness/validate.py --trace-dir harness/traces --replay /tmp/replay
```

The script exits non-zero if any FIFO/LRU/LFU point exceeds the tolerance,
so it works as a regression check and not only as a report generator.
`--render-only` rebuilds this document from `harness/validation.json`
without rerunning the comparison. Traces are gitignored; they are tens of
megabytes and reproducible from the fetch script.

## What this caught

The gate is not a formality: the first run of it disagreed with
libCacheSim by **0.0153** on LRU request miss ratio, fifteen times the
tolerance above.

The cause was object-size handling on a cache hit. This harness had been
updating a resident object's size when the trace re-requested the same id
at a different size. libCacheSim does not: `cache_find_base` updates only
`next_access_vtime` and `freq`, so an object keeps its admitted size until
it is evicted.

That would be a footnote on most workloads. On these traces **63% of
objects appear at more than one size and 70% of requests touch such an
object**, so the resize path fired constantly and shifted eviction
decisions throughout the run. With the behavior matched, agreement went to
the numbers reported above.

The lesson worth keeping: a policy implementation can look correct, pass
hand-computed unit tests, and still be wrong about the workload, because
the disagreement lived in the cache's accounting rather than in any
policy.

## Deliberate divergences

Neither of these affects the numbers above, but both are real and are
recorded so they are not rediscovered later as surprises.

- **Belady admits objects needed later than every resident.** A strictly
  optimal policy would decline them. libCacheSim admits, because the
  object being inserted is not yet resident and so cannot be chosen as its
  own victim, and this harness matches it so the comparison is of one
  algorithm rather than two. Combined with Belady being provably optimal
  only for uniform object sizes -- variable-size offline caching is
  NP-hard -- the reported OPT is a strong upper bound, not a proven
  optimum. Under `--ignore-obj-size` it is genuinely optimal.
- **S3-FIFO parameters are set explicitly on both sides** rather than
  relied upon as defaults, so the two tools cannot agree by coincidence
  or diverge silently if a future libCacheSim changes them.

## What this does not cover

- **One workload family.** All three traces are Alibaba block traces.
  They have variable object sizes, which is what made them useful here,
  but a key-value or CDN workload could exercise paths these do not.
- **No warmup.** Both tools run the whole trace cold, because libCacheSim's
  `process_trace` has no warmup notion to match. `--warmup-frac` is
  covered by unit tests, not by this cross-check.
- **Miss ratios only.** The other reported metrics -- ns/op, peak policy
  metadata, metadata per resident object -- have no libCacheSim
  counterpart to compare against and are unvalidated here.
- **No TTL and no deletes.** These traces carry neither.
